## 주요 주의사항 요약

1. **v1/v2 타입 이름 충돌**: `HeaderGroup`, `SortState`, `ValidationResult`, `RowActionsConfig`, `EditComponentProps` 는 v1/v2 양쪽에 존재.
   `src/components/table/index.ts` 에서 **`DataTableV2` 접두사**를 붙여 내보낸다 (`DataTableV2SortState` 등).
   특히 `SortState` 는 정의 자체가 다르다 — v1 은 `column: keyof T | null`, v2 는 `column: keyof T`.
   (2026-08-09 CMS 이관 중 수정. 그 전에는 아예 export 하지 않아서 사용처가 내부 경로를 직접 import 해야 했다)

2. **React.memo Row 제네릭 함정**: `DataTableV2Row` 는 memo + 제네릭 T. Row 에 새 required prop 추가하면 콜사이트 (`data-table-v2.tsx` 내부 `<DataTableV2Row>`) 에 반드시 함께 넘겨야 함. 안 넘기면 TS 가 T 를 constraint 로 fallback 하고 여러 prop 이 타입 에러 발생 → 원인 찾기 어려움.

3. **dist/ 커밋 대상**: Git URL 직접 설치 방식이라 dist 도 저장소에 포함. 커밋 전 반드시 `npm run build`.

4. **커밋 메시지 AI 서명 절대 금지**: `Co-Authored-By: Claude`, `🤖 Generated with ...` 등. 사용자가 명시적으로 요청한 경우만 예외.

5. **UI 변경은 자동 테스트만으로 완료 아님**: `npm test` (563 tests, SDS-42 이후) 통과해도 실제 인터랙션 (클릭, 편집, 드래그, 리사이즈, 필터 팝오버 등) 은 Storybook 브라우저에서 직접 확인.

6. **행 액션 위치는 왼쪽**: 삭제 아이콘 (`rowActions.showDelete`), 하단 추가 버튼 (`rowActions.showAdd`) 둘 다 체크박스/확장 뒤 위치 (v1 일관성).

7. **Row 배치는 `top: translateY`** (SDS-36 에서 `transform: translate3d` → `top` 으로 전환됨). dnd-kit sortable 이 layout 좌표 기반으로 동작하기 때문. 신규 배치 로직 추가 시 이 전제 유지 (transform 프로퍼티는 dnd-kit 드래그/시프트 전용).

8. **좌측 컨트롤 컬럼 순서**: [드래그 핸들] → [체크박스] → [확장] → [삭제] → [데이터 컬럼]. 신규 좌측 sticky 셀 추가 시 이 순서 지키기.

9. **헤더 셀 layout 3슬롯 구조** (SDS-42): `[헤더명 + 정렬 인디케이터]` · `[필터 아이콘]` · `[미래 확장 슬롯]`. `alignClass` 는 슬롯 1 내부에만 적용. 슬롯 1 에 `overflow-hidden`, 헤더명 span 에 `truncate` 로 컬럼 폭 부족 시 헤더명이 잘리고 필터 아이콘은 유지.

10. **헤더 셀 모두에 `headerBg`** (SDS-42): right pinned 없는 케이스에서도 우측 스크롤 시 흰 gap 안 보이도록 pinned 여부 무관하게 모든 헤더 셀에 bg 부여. 신규 헤더 셀 로직 추가 시 이 전제 유지.

11. **리사이즈 시맨틱 (SDS-43 완료)**: v2 리사이즈는 **독립 방식** (AG Grid 기본 모드). 대상만 폭 변경, 다른 컬럼은 그대로. 최초 리사이즈 시 flex 컬럼은 스냅샷으로 fixed 전환됨. `col.minWidth` 존중. 헤더 셀 `[data-column-key]` 로 스냅샷 매핑. 리사이즈 관련 개선은 이 방향성 유지.

12. **rowGrouping 렌더 방식 (SDS-37 완료)**: div/absolute 배치용으로 v1 의 HTML rowSpan 대체 = span=0 placeholder + span>1 head 셀 컨텐츠를 `absolute + height=spanHeight + z-[5] + opaque bg` 로 세로 확장. **row inner border-b 는 SDS-43 대로 유지** (v1 middle row 스킵 반사적 이식했다 부작용 발견 → 원복. head 셀 wrapper 가 병합 영역 border 를 자동으로 시각 커버). 그룹 hover 는 `getGroupHovered` 로 middle row hover 시 head 셀 함께 highlight. `rowReorderable` 은 자동 OFF (병합 셀 드래그 시 붕괴).

13. **리렌더 최적화 원칙 (SDS-38 완료)**: (a) SortableContext 는 rowReorderable 시만 렌더 (context subscription 카스케이드 방지), (b) 사용자 콜백은 useStableCallback 흡수, (c) 훅 내부 state 는 ref 로 흡수해 파생 콜백 stable, (d) row bg 는 CSS `:hover`/`group-hover:` 로 (state 무관), (e) pinned shadow 는 CSS `group-data-*` + imperative DOM data-attr, (f) 파생 배열/객체는 useMemo. 신규 상호작용 추가 시 이 원칙 유지. **React DevTools Profiler 는 Radix Popover 등 외부 라이브러리 내부 렌더까지 aggregate 로 보여줌** — 정확한 최적화 검증은 console.log 실측.

14. **가상화 (SDS-38 완료)**: `virtual?: boolean | VirtualConfig` opt-in. 기본 OFF. **비활성 시 `getScrollElement: () => null` 로 virtualizer 가 scroll listener 부착 안 함** → 가로 스크롤 등 무관 이벤트로 인한 리렌더 없음. Row 에 `measureRef`/`dataIndex` 로 자동 측정. rowGrouping 조합 시 `renderIndices` 에 그룹 head 인덱스 강제 추가.

15. **임시 수정 금지**: 문제 발생 시 임의로 우회하지 말고 사용자와 먼저 논의. 원인 분석 → 해결 방법 제시 → 합의 후 진행. CLAUDE.md 의 "작업 진행 규칙" 참고.

16. **날짜**: 2026-08-04 기준 (SDS-38 완료. 다음 SDS-39 회귀 검증).

## [DS] 상용 데이터그리드 도입 검토

### 배경

물류 시스템(CMS/LMS)의 테이블 화면에서 실무자들이 엑셀 수준의 편집/조작 UX를 요구하고 있음. 반면 CMS는 외부 고객사에도 노출되는 프로덕트이므로, 도입할 그리드는 아래 조건을 동시에 충족해야 함:

- 디자인시스템과 자연스럽게 통합되어 프로덕트 UI 톤 유지
- 서버에서 페이지네이션된 대용량 데이터를 안정적으로 처리
- 엑셀에 준하는 편집/복붙/export UX 제공

디자인시스템에서 자체 개발 중인 DataTable v2 로는 스프레드시트 특화 기능(수식 엔진, 클립보드 양방향 복붙, xlsx export, fill handle 등) 구현 비용이 크고 완성도 확보가 어려움. 이에 상용 그리드 도입 후 디자인시스템 토큰을 얹어 Wrapper 형태로 노출하는 방식을 검토함.

### 검토 기준

| 항목 | 세부 |
|------|------|
| 리액트 지원 | React 18+ 공식 지원, 성숙한 API |
| 엑셀 UX | 셀 편집, 복붙, 셀 범위 선택, 수식, xlsx import/export, undo/redo, fill handle |
| 대용량 데이터 | 클라이언트: 가상화 / 가상 스크롤. 서버: Server-Side Row Model 등 서버 페이지네이션/정렬/필터 지원 |
| DS 통합 | CSS 변수 기반 테마, 우리 토큰(색/spacing/typography) 매핑 가능 여부, Tailwind/shadcn 통합 사례 |
| 프로덕트 UI 톤 | 외부 고객사 노출 화면에서 이질감이 없는 데이터 그리드 톤 (스프레드시트 톤 X) |
| 가격 | per developer 라이선스 기준 예측 가능성 |
| 문서/커뮤니티 | 유지보수 지속성 |

|------|---------------------|-------|-----------------------------|---------|---------|------|

### 상세

#### 1순위 — AG Grid Enterprise

**적합한 이유**
- 리액트 공식 패키지 제공. React 18+ 지원 성숙
- 대용량 서버 데이터 처리에 강함. 그리드가 서버에 페이지/정렬/필터 상태를 규격화된 형태로 요청하고 응답을 자동 관리하는 방식(SSRM)이라 우리 페이지네이션 API에 그대로 연결 가능. 행·열 가상화 기본 탑재
- 근본이 "데이터 그리드" 톤이라 우리 DS 를 얹었을 때 프로덕트 UI 로 자연스러움
- 100+ CSS 변수 + Theme Builder GUI 제공. 우리 토큰(색/폰트/spacing) 매핑 가능
- 엑셀 UX: 셀 편집, 복붙(양방향), undo/redo, 셀 범위 선택, 컨텍스트 메뉴, xlsx export(스타일/formula 유지), 마스터-디테일, 피벗까지 커버
- 문서/커뮤니티/샘플 규모 최대 → 러닝커브 짧고 유지보수 리스크 낮음

**고려 사항**
- 완전 브랜딩은 100+ 클래스명(`ag-header`, `ag-row` 등) 타겟팅 세밀 튜닝이 필요. 초기 통합 시간 투입 필요
- 스프레드시트 수식(`=SUM` 등) 은 미지원. 실무자 요구에 수식이 필수면 재검토 필요
- 가격이 개발자 수 기준. AG Grid 를 직접 다루지 않더라도 해당 UI 코드베이스에서 작업하는 모든 개발자(계약직/외주 포함)가 라이선스 카운트에 포함되는 정책이라, 팀 확대 시 비용 상승 폭이 큼. 라이선스 대상 범위는 계약 전 반드시 정밀 확인 필요

**가격**
- Perpetual $999/dev (1년 업데이트 포함)
- Subscription: Single Application $995–$1,295/dev/year, Multi Application $1,495–$1,995/dev/year

#### 2순위 — Syncfusion

**적합한 이유**
- 리액트 공식 지원. 그리드 톤
- 서버 사이드 오퍼레이션 정식 지원 (페이지네이션/정렬/필터) + 가상화
- 엑셀 UX: Excel-like 필터, xlsx/PDF export, 편집 기능 등 폭 넓음
- Theme Studio GUI 제공으로 초기 브랜딩 러닝커브 완화

**고려 사항**
- 그리드 단독보다 Essential Studio 전체 스위트 구매 성격이 강해서, 그리드만 필요한 우리 케이스에 비용 효율이 AG Grid 대비 낮을 수 있음
- 그리드 외 컴포넌트 톤이 우리 DS 와 충돌 가능성 있음 (그리드만 부분 도입 시 톤 정합성 확인 필요)
- 라이선스 조건/가격이 공개되어 있지 않아 예측 가능성 낮음. 계약 전 별도 상담 필요

**가격**
- 별도 상담 필요 (Community License 는 회사 매출 $1M 미만 + 개발자 5인 이하 + 총 직원 10인 이하 조건. 당사는 해당 없음)

#### 후보에서 제외

- **Handsontable / Jspreadsheet** — 엑셀 UX 자체는 최상급이고 shadcn/Tailwind 통합 레시피(Handsontable)까지 공식 제공되지만, 시각적 톤이 근본적으로 스프레드시트에 가까움 (셀 그리드 라인, 헤더/필터 UI, 툴바 등). CSS 변수로 색은 조정 가능하나 프로덕트 UI 로 정렬시키는 데 한계가 있어 외부 고객사 노출 화면에 부적합. 서버 사이드 페이지네이션 성숙도도 AG Grid 대비 낮음
- **Bryntum Grid** — 스케줄러/프로젝트 그리드 방향에 특화되어 엑셀 UX 특화도 낮음

### 우선 검토안

**1순위 후보: AG Grid Enterprise**

- 리액트 지원, 대용량 처리(가상화 + SSRM), 프로덕트 UI 톤, DS 통합 유연성, 실무 엑셀 UX(수식 제외), 문서/커뮤니티 성숙도 모두 우리 요구에 부합
- 도입 시 디자인시스템에서는 Wrapper 컴포넌트(예: `EnterpriseDataGrid`)로 감싸 DS 토큰을 주입하고 자체 API 를 노출하는 방식이 적절

**대안: Syncfusion**

- 라이선스 조건 확인 후, PoC 시 병행 검토 가치는 있음
- 다만 우리 케이스(엔터프라이즈 데이터 그리드 특화 요구)엔 AG Grid 성숙도가 더 부합함

### 다음 단계

- 실무자 엑셀 요구 세부 파악 (수식 필요 여부에 따라 결론이 흔들릴 수 있음)
- AG Grid Enterprise + Syncfusion PoC — 실제 데이터 볼륨 + 서버 페이지네이션 연동 + DS 토큰 매핑까지 포함
- 라이선스 조건 정밀 확인 (개발자 수 산정 기준, SaaS/재판매 조항)
- Wrapper 컴포넌트 설계 (기존 `Table`, `DataTable` 계열 API 일관성 유지)
- 자체 개발 중인 DataTable v2 와의 역할 분리 정리 (v2 는 경량 테이블, 상용 그리드는 대용량/엑셀 UX 케이스)

### 디자인시스템 적용 시 검토 사항 및 대략 공수
